# ドキュメントを横串で監査して直す

**古い記述を 1 つ見つけたら、同じ種類の古さが他にもあると考えます。**
指摘されたファイルだけ直して、次の報告で「これもありました」と別のファイルを
出す、を繰り返さないこと（2026-10-12 にそれをやり、ユーザーに
「後出しジャンケンはやめて欲しい」と言われた）。

**全部を先に洗い出し、一覧にしてから一度に直し、一度に報告します。**

## 0. 機械で拾えるものを先に回す

```bash
make check-links          # 追跡ファイル基準のリンク切れ
make check-stale-docs     # 一度直した古い記述が戻っていないか（RULES）
```

`check-stale-docs` の規則は `scripts/check-stale-docs.py` の `RULES`。
**今回の監査で見つけた「同じ間違いが繰り返し出る種類」は、最後に RULES に足す**
（手順 6）。

## 1. 対象を全部挙げる

```bash
git ls-files '*.md' | wc -l                         # 文書
git ls-files | grep -vE '\.md$'                     # コード・設定（コメント・ヘルプ文）
```

公開面はリポジトリの外にもある。**ここも対象に含める:**

| 場所 | 取り方 |
| --- | --- |
| Docker Hub の Overview と短い説明文 | `curl -s https://hub.docker.com/v2/repositories/ishinokazuki/kimigayo-os/`（`full_description` / `description`） |
| GitHub の Wiki | `git clone https://github.com/Kazuki-0731/Kimigayo.wiki.git <scratchpad>/wiki` |
| リポジトリの説明・トピック | `gh repo view --json description,homepageUrl,repositoryTopics` |
| 開いている Issue | `gh issue list --state open` |
| イメージ自身の名乗り | `/etc/motd`・`/etc/os-release`・OCI ラベル（`docker inspect`） |

**「何を見て、何を見ていないか」を報告に必ず書く。** 見ていない場所があると、
それが次の「後出し」になる。

## 2. 事実の一覧を先に作る

監査の前に、**文書間で揃えるべき現在の事実**を 1 枚にまとめ、
スクラッチパッドに置く（例: `<scratchpad>/decisions.md`）。担当が分かれても
同じ値・同じ言い方に揃えるため。

- 出典は `CLAUDE.md`（実測値・方針）、`versions.mk`、`git describe`、
  ワークフロー、`scripts/`、公開イメージ（`docker run` で確かめる）
- **文書どうしで値が食い違ったら、記録（`git log -S`・ベンチマークの生データ）で
  どちらが正しいか決めてから**一覧に書く。決められないものは「未確認」と書く
- 監査の途中で事実の誤りが分かったら、一覧を直して**全担当に伝える**
  （2026-10-12 には「`ps -o` は Extended だけ」を途中で訂正した）

## 3. 分担して全行を読む

ファイルを 5〜6 の束に分け、`docs-reconciler` を束ごとに並列で走らせる
（同じファイルを 2 人に持たせない）。

- 束の分け方の例: トップレベル（README・SPECIFICATION・DEVELOPMENT など）／
  利用者向け＋examples／開発者向け＋deployment／性能・運用・計画書／
  セキュリティ＋Issue テンプレート／`src/`・記録類・`CLAUDE.md`・`.claude/`
- 渡すもの: 担当ファイルの一覧、事実の一覧のパス、「全行読んだ」と件数を返すこと
- **コマンドの可否は公開イメージで実際に試させる。** BusyBox は GNU と違う
  （`ps aux`・`find -size +10M`・`wget --tries` は動かない）

## 4. 集約して、直すものと判断を仰ぐものに分ける

| 種類 | 扱い |
| --- | --- |
| 文書の誤り・古い記述・言い過ぎ | **全部直す** |
| 歴史の記録（CHANGELOG・当時の計画書） | 本文は消さない。冒頭の注記で「当時の記録」と明示し、無効になった値と結論を書く |
| 実装の不具合（コードを変えないと直らない） | 文書は**今の挙動どおり**に書き直し、実装は一覧にして判断を仰ぐ |
| ファイルの削除・ライセンス・設定の変更 | 判断を仰ぐ（CLAUDE.md「削除指示を受けたら」「指示の範囲を超えない」） |

## 5. 直す

- 修正も束ごとに並列でよい（監査した担当にそのまま直させると、指摘の文脈を持っている）
- **コミットはメインがファイルごとに切る**（1 修正 = 1 コミット）。担当にはコミットさせない
- 担当が担当外のファイルを触っていないか、`git status` で確かめてからコミットする
- examples のように動くものは、**ビルドして動かして**確かめる

## 6. 再発を止める

- 繰り返し出た種類の古い記述は `scripts/check-stale-docs.py` の `RULES` に足す。
  **監査前のツリーで検出でき、今のツリーで 0 件**になることを確かめる:

  ```bash
  W=<scratchpad>/oldtree
  git worktree add -q --detach "$W" <監査前のコミット>
  (cd "$W" && python3 "$OLDPWD/scripts/check-stale-docs.py" | head -3)
  git worktree remove --force "$W"
  make check-stale-docs
  ```

- 判断が要る種類（言い過ぎ・前提のずれ）は `docs-reconciler` の
  「事実と異なる主張」の実例に足す

## 7. 一度で報告する

1. 何を見たか・見ていないか
2. 直したもの（件数とコミット）
3. 直さなかったものと理由
4. 判断を仰ぐもの（実装・削除・ライセンス・外部サービスの操作）を**全部まとめて**
5. ユーザー操作が要るもの（Docker Hub の貼り直しなど）

**途中経過で「これもありました」を出さない。** 担当の報告が出そろうまで待つ。
